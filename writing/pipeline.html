From a week to a day: a lab and radiology pipeline for many clinics

I cut lab and radiology batch turnaround at Mesh Bio from about a week to a day by rebuilding the pipeline that brings clinic files into the platform. A new clinic became a configuration job, not a code change.

Where we started

Mesh Bio is a Singapore health-tech company working with private healthcare providers. Its most widely adopted product was a health screening workflow that used predictive analytics to score each patient's risk and recommendation logic to build the screening reports. I facilitated that by building the pipelines that fed it.

Clinics and labs sent us lab and radiology files as HL7 and CSV. Inside those formats, every clinic or lab used its own coding system, naming conventions and units. The pipeline ran in every market we served.

The first version was hardcoded: an S3 bucket fed a Lambda function that transformed the file and wrote to the database, with a separate Lambda for every clinic and lab combination. That meant duplicate code, many Lambdas to deploy, and code rewrites for small changes. Scheduled files arrived at the start of every hour, about 10,000 records an hour in Singapore alone, and clinics could also submit on demand. Those on-demand files had to be processed as fast as possible.

What it had to do

I had to make the pipeline handle many clinics without a code change for each one. It had to work fast on the hourly burst and on demand. It also had to run inside two limits: the Lambda concurrency limit of our AWS account, which other applications' Lambdas shared, and the MongoDB connection pool limit. Above all, the pipeline had to block any record it could not match to the right patient.

The redesign

I started the redesign in the first quarter of 2023. I designed it, worked through the design with our CTO, and my manager approved it. Going from one Lambda to a full orchestration took about 6 to 8 months, and we extended it afterwards for new downstream projects and new file formats.

Before:  S3 -> Lambda <-> DB     (one hardcoded Lambda per clinic and lab combination)

After:   S3 -> EventBridge Pipes (SQS + Lambda)
              -> Step Functions (Lambda steps)
                   1. read the file signature
                   2. identify the lab and the clinic
                   3. fetch that source's config from the DB
                   4. process the message in several steps
                   5. insert into the DB

I made three decisions.

Differences live in configuration, not code. The Lambda read the file signature, worked out which lab and clinic sent it, and pulled the matching config from the database. A new clinic or file format meant a new config and signature. I could change the configuration for one clinic and lab combination without putting the workflow of any other clinic at risk, and I could test new functions and pipelines far more easily. For two or three lab vendors I also built the upstream MLLP endpoint that received HL7 and wrote the files to S3 for the pipeline.

Batching, with a count check. I used SQS to queue the work and wrote code that catches many records in one file and processes them as a batch. That kept the number of running Lambdas and open database connections inside the limits. Many files held several patient records, so I used pattern matching to find where each record started and ended. A check then confirmed the number of records extracted matched the number expected, and each record was isolated before anything went downstream. Processing one record per invocation would have been simpler. The count check and isolation are what made batching safe.

Block bad data, do not write it. I used CloudWatch to separate error types and alert me and customer success. A count mismatch was rare. When one happened, we contacted the lab vendor to fix their submission.

Once, a vendor moved to a different system without telling us. Data surged and the file pattern changed. The pipeline was already configurable, and the exception handling stopped the script instead of letting wrong data through. My solutions engineer and I handled it in a single day, and no wrong data reached a patient profile.

Parsing 10,000 or more records could take 5 to 7 minutes. Clinics did not need to know when a file arrived. They opened the patient profile and the data was there.

What changed

Lab and radiology batch turnaround went from about a week to a day. The pipeline also helped cut onboarding per clinic from 3-5 days to under 1 day.

I was promoted to Solutions Architect and became the hiring manager for a team of 2-3 solutions engineers. I handed this work to them and supervised its expansion and the development of new pipelines and APIs on top of it.
