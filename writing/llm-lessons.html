Lessons from using an LLM to clean up messy clinic data

Written from work I did in 2025, using Claude through Amazon Bedrock.

I built an AI clean-up pipeline with LangGraph, Claude on Amazon Bedrock, Pydantic and ChromaDB. Per-submission time improved from about 1 hour to 6-10 minutes, including human review, for 30+ clinics.

The problem

Mesh Bio is a Singapore health-tech company working with private healthcare providers. Clinics sent patient submissions for its health screening workflow as CSV and Excel files. Every vendor used its own column names, and each customer had its own list of health screening package names. A person cleaned each submission by hand, which took about an hour.

I had to get an LLM to turn those files into clean, structured output a reviewer could trust. The model had to follow instructions closely, stay within cost, and fit the work inside the context window of the models available at the time.

Six lessons

1. Start with the raw file and read what the model does. I began with the file and the expected output in the system prompt and the first message, and watched the patterns. Testing across models showed that Claude Sonnet followed instructions best, so I used it.

2. If the model writes the same script every turn, make it a tool. Given a CSV or an Excel file, the model wrote a Python script from scratch each time. I turned those scripts into tools: look at the data, map column names, count records, write a new output CSV and track progress. The model then spent its effort on transforming the data.

3. Search for reference data. The list of package names was long and different for each customer. I gave the model a ChromaDB vector search to find the closest match. A vendor might send "Silver Male" when the exact name was "Silver Package Male". If the vendor sent only "Silver Package", the model used the patient's gender to choose the Male or the Female package.

4. Work in steps, because of the context limit, context rot and cost. The context window of the models at the time was smaller than it is now. Feeding the whole file at once also cost more, and the model got worse as the context grew. The LangGraph flow moved in steps:

extract the required fields (test name, value, units, abnormal flag)
  -> structure them into a JSON schema
  -> fetch parameter names through our API
  -> map test names to our internal names and codes
  -> call the validation endpoint
  -> read the feedback and correct
  -> validate again
  -> write the cleaned file

5. Check the output outside the model. The validation endpoint used Pydantic. It checked that patient identifiers were in capitals, that phone numbers had the country code separate from the number and were valid, and that emails were valid. One Pydantic model handled many records. In testing and on live submissions, when the first row passed, the rows after it passed the same checks. The model processed 10 to 20 records at a time. I reached this flow after many tests.

6. Keep a person in the loop. The model did not submit anything. It produced a cleaned file, and a human reviewer checked it and submitted it.

I also built and tested a public endpoint that connected vendors to our LLM, in October and November 2025. I did not release it: it needed more testing, and its forecast cost was a factor.

The outcome

Per-submission time went from about 1 hour to 6-10 minutes, including human review, for 30+ clinics. A reviewer checked every output.
